# Threat model

Scope: the contracts in `contracts/src`, the facilitator (`src/facilitator`), the resource server (`src/server`), the agent (`src/agent`) and the validator (`src/validator`), as run by this repository on a local anvil chain. Nothing here has been audited, and nothing is deployed with real funds. TestUSD is a local test token that refuses to deploy on any chain other than 31337.

Vulnerability classes are named after the [OWASP Smart Contract Top 10 (2026)](https://scs.owasp.org/sctop10/) where one applies.

## Assets

| Asset | Where it lives | Why it matters |
|---|---|---|
| Payer funds (EOA) | TestUSD balance of the payer | An `exact` or `escrow` signature moves them. |
| Principal funds (agent smart account) | TestUSD balance of the `AgentAccount` (or of its counterfactual address before deployment) | The agent process holds a session key that can spend them. |
| Escrowed funds | `PaymentEscrow` balance | Held between opening and delivery/refund. |
| Settlement receipts | `SettlementLog` storage | They are the only thing that makes feedback count, so forging one forges reputation. |
| Reputation | `ReputationRegistry` | Buyers rely on it to choose services. |
| Validation scores | `ValidationRegistry` | Signal that a service's outputs are reproducible and tied to real payments. |
| Service payment address and its history | `IdentityRegistry` wallet checkpoints | The agent only pays `payTo` addresses that match it; feedback is checked against the wallet in force at settlement. |
| Paid results and request data | Resource server memory (escrow results, work documents) | Results were paid for; work documents carry the raw request, which may contain personal data. |
| Validator gas and network position | Validator process | It sends a transaction per answered request and fetches URLs named in requests. |

## Actors and trust

| Actor | Trusted for | Not trusted for |
|---|---|---|
| Payer / principal | Its own keys | n/a |
| Agent process (session key) | Nothing beyond its on-chain policy | Amounts, payees, frequency: all bounded by `BudgetExecutor` |
| Facilitator | Liveness only (it pays gas and relays) | Amount, payee, resource, reporting honestly. Every settlement is re-checked from the transaction receipt by the server and by the agent, against the receipt id the server derives from the signed payload itself. |
| Resource server | Doing the work it was paid for | Its `PAYMENT-REQUIRED` challenge: the agent re-derives the resource hash, only pays the `payTo` registered in the identity registry, and bounds the validity and escrow windows it accepts. Its validation documents: the validator ties them to the on-chain receipt. |
| Agent owner (ERC-8004) | Its card and its wallet choice | Feedback on its own agent: past receipts stay valid whatever it does with the wallet later. |
| Validator | The score it posts under its own address | n/a (readers choose which validators to count) |
| Requester of a validation | Nothing | Anyone can register an agent and name any validator, so requests are untrusted input to the validator. |
| Deployer | Wiring the contracts in one broadcast | Anything after `SettlementLog.seal()`: ownership is renounced there. It remains TestUSD's minter (local faucet). |

## Attack surface and mitigations

| # | Threat | OWASP SC 2026 | Mitigation | Evidence |
|---|---|---|---|---|
| T1 | Facilitator changes the amount or payee of an `exact` payment | Improper input validation | The EIP-3009 signature covers `to` and `value`; the token rejects any change. | `SettlementLogTest.test_RevertWhen_FacilitatorChangesAmount/Payee`, e2e `exact: changed amount, payee or resource all revert on-chain` |
| T2 | Facilitator re-attributes a payment to another resource | Improper input validation | The nonce is `H(tag, resourceHash, salt)` with the sequence bits cleared; changing the resource needs a second preimage. | `testFuzz_RevertWhen_ResourceDiffers`, `test_RevertWhen_FacilitatorForgesNonceForOtherResource` |
| T3 | Facilitator lies about a settlement (fake or unrelated tx hash, reverted tx, somebody else's receipt) | Business logic | Server and agent call `confirmSettlement`: the receipt must contain a `ReceiptRecorded`/`EscrowOpened` event from the deployed contract with the expected payee, amount and resource; the server also requires the receipt id it derives from the payload (payer + nonce). | e2e `refuses to serve when the facilitator claims success with an unrelated transaction`, `... redirects the payment and reports its reverted transaction`, unit `matchSettlementLogs` |
| T4 | Replay of a payment header | Replay | Token nonces are single use; intent nonces are single use per account (kept across module reinstalls); the server marks each receipt as consumed for as long as it could be claimed (the claim window). | e2e `a PAYMENT-SIGNATURE buys exactly one call`, `serves a replayed payment only once...`, `test_RevertWhen_NonceReplayed`, `test_ReinstallResetsAllowlistButKeepsNonces` |
| T5 | Cross-resource replay (same payment, other body/path/server) | Replay | The resource hash covers method, origin, path, sorted query and body SHA-256; the server only accepts payments whose requirements match the request exactly. | e2e `a payment for one resource is refused for another body, path or server` (the server case runs a second server on another port) |
| T6 | Stale or long-lived authorization | Replay | `validAfter`/`validBefore` enforced on-chain; the facilitator bounds `validBefore` by `maxTimeoutSeconds`; the agent refuses challenges whose `maxTimeoutSeconds` exceeds its own bound (default 300 s). | e2e `an expired authorization is refused before any gas is spent`, unit `refuses authorizations that would stay valid longer than the client allows` |
| T7 | Compromised or buggy agent overspends | Access control | Per-call cap, rolling-window budget, payment-rate limit, payee allowlist and session expiry enforced by `BudgetExecutor`; the session key cannot install modules or execute on the account. | Invariants I1–I5, `test_RevertWhen_SessionKeyTriesToInstallModules` |
| T8 | Executor module escapes the policy with `delegatecall` | Unsafe delegatecall | `AgentAccount` rejects delegatecall mode for every caller and reports it unsupported. | `test_RevertWhen_ExecutorRequestsDelegatecall`, `test_RevertWhen_OwnerRequestsDelegatecall` |
| T9 | Counterfactual account front-run with an attacker session key, or bricked by the clock | Front-running / denial of service | The CREATE2 salt commits to owner and full policy payload. The executor does not check the session expiry at install time, so a funded predicted address stays deployable after `validUntil`; an expired session simply cannot spend until rotated. | `test_Factory_SaltBindsPolicy`, `test_Factory_CounterfactualAddressDeployableAfterSessionExpiry`, `test_InstallWithExpiredSessionThenRotate` |
| T10 | Forged receipts inflate reputation | Access control | Only the log itself, the budget executor and the escrow can record receipts; the set is frozen by `seal()`, which also renounces ownership. | `test_Wiring`, `test_UnsealedLifecycle`, `test_RevertWhen_RecordByNonRecorder` |
| T11 | Sybil / self feedback | Business logic | Feedback needs a receipt where the author paid the agent's wallet as it stood at settlement; each receipt backs one feedback; owner, operators and the current wallet are refused; `getSummary` requires an explicit client filter and weights each entry by its receipt amount. | Invariants I9–I11, `test_RevertWhen_OwnerOperatorOrWalletRatesItself`, `test_GetSummaryWeightsByReceiptAmount` |
| T12 | Escrow funds stuck or double-spent | Business logic | Exactly one terminal state (`Released` before/at the deadline, `Refunded` after); anyone can trigger the refund. | Invariants I6–I8, `testFuzz_DeadlineBoundary` |
| T13 | Escrow terms redirected by the relayer | Front-running | `receiveWithAuthorization` is callable only by its `to` (the escrow); the nonce commits to payee, resource and deadline. | e2e `escrow: changed payee, deadline, amount, resource or escrow contract all revert` (the escrow case deploys a second `PaymentEscrow`) |
| T14 | Fee-on-transfer or non-standard token behaviour | Unchecked external calls | Exact balance-delta checks after every transfer; SafeERC20-equivalent return-data check in the executor. | `NonStandardTokenTest` |
| T15 | Server phishing (payTo swapped, price inflated, unknown contracts, escrow locked for long) | n/a (off-chain) | The agent pays only the registry `agentWallet`, below its own price cap, through the deployed settlement contracts, for the resource hash it computed, and refuses escrow delivery windows above its bound (default 1 h). | `clientPolicy.test.ts`, e2e `refuses to pay a price above the client-side cap` |
| T16 | PII in payment metadata reaches logs or the chain, or leaks through served documents | n/a (privacy) | Strict zod metadata schema + regex redaction; the logger redacts every string except 0x-hex and decimals under known numeric keys; on-chain strings go through `onchainString`. Work documents must carry the raw request (the validator needs it to match the receipt), so the server serves one only to the validator named on-chain, which signs an EIP-191 challenge; escrow results need the access token returned with the `202`. | `pii.test.ts`, e2e `logs every receipt without leaking PII`, `serves a work document only to the validator named on-chain`, `serves an escrowed result only to the holder of its access token` |
| T17 | ERC-1271 signature replay across accounts owned by the same key | Signature malleability / replay | `AgentAccount` accepts owner signatures only in ERC-7739 nested form, bound to the account's own domain. | `test_ERC1271_RawOwnerSignatureRejected`, `test_ERC1271_NestedTypedData` |
| T18 | Paid without service after a failure past settlement (lost facilitator response, transient RPC error, crash) | Business logic | Receipt reads are retried with backoff. A client retry with the same `PAYMENT-SIGNATURE` reaches the idempotent `/settle` even when `/verify` reports the nonce consumed or the window closed; the call is served if the on-chain settlement is this payment's, is not consumed, and settled within the claim window (default 600 s). The agent retries transient failures by itself. | e2e `a payment that settled but was not served can be claimed by retrying it` (6 cases) |
| T19 | Agent owner censors feedback by rotating, clearing or transferring away the wallet | Business logic | `IdentityRegistry` checkpoints every wallet change; feedback is checked with `wasAgentWalletAt(agentId, payee, settledAt)`. | `test_FeedbackSurvivesWalletRotationClearingAndTransfer`, invariant I11 with a handler that keeps rotating the wallet |
| T20 | One payment backs feedback on several agents (shared wallet) | Business logic | A wallet serves at most one agent at a time (`WalletInUse`), so a receipt identifies the agent it paid. | `test_RevertWhen_ReceiptBacksFeedbackOnAnotherAgent`, `test_RevertWhen_WalletServesAnotherAgent` |
| T21 | Dust receipts buy full-weight reviews | Business logic | Values live on a fixed scale (normalized to [-100, 100]); `getSummary` weights each entry by its receipt amount, so a 1-unit payment buys a 1-unit weight. | `test_DustReceiptBuysDustWeight`, `testFuzz_SummaryBounds` |
| T22 | Validation request hash squatted by another agent | Denial of service | Validations are keyed by `(agentId, requestHash)`. | `test_RequestHashSquattingByAnotherAgentHasNoEffect` |
| T23 | Dishonest server gets a high validation score for fabricated or cherry-picked work | Business logic | The validator requires that the work document's receipt exists, paid the agent's wallet at settlement, and commits to exactly the document's URL and raw body; the URL must be the claimed service on the agent's registered endpoint; it then re-executes the paid body. Any mismatch scores 0. | unit `judgeWorkDocument` cases, e2e `validation is tied to the payment it claims to validate` (fabricated input and output, nonexistent receipt) |
| T24 | Hostile validation requests block the validator, make it fetch arbitrary URLs (SSRF) or hang it | Denial of service | Each request is handled in isolation (no throw escapes); documents are fetched only from the origin of the agent's registered x402 endpoint, without redirects, with a timeout and a size cap; fetch failures are retried with backoff then given up; the event scan resumes from a stored block cursor. | e2e `the validator contains hostile validation requests`, unit `readBody`, `originOf`, cursor tests |
| T25 | Facilitator reports another settlement of the same nonce (two authorizations, one nonce) as this one | Business logic | `findExisting` compares the stored payer, payee, amount and resource with the request and answers `nonce_already_used_mismatch` otherwise. | e2e `refuses a settlement of the same nonce with other terms, and so does the facilitator`, unit `settlement.test.ts` |
| T26 | Facilitator or server memory grows with traffic | Denial of service | In-flight settlements are dropped once finished (the chain answers repeats); consumed receipts, work records, validation documents and jobs expire with the claim window, the retention period or the escrow deadline. | unit `keeps nothing once a settlement is over`, e2e `the resource server state is bounded` |

## Known limitations

1. **Direct token submission.** Anyone who sees an `exact` authorization can call `TestUSD.transferWithAuthorization` directly. The payee still receives exactly the signed amount, but no receipt is recorded and the facilitator then reports `nonce_already_used`, so the call is not served (the recovery path of T18 needs a receipt). The payer loses the payment without service. Canonical x402 facilitators have the same exposure (they submit to the token directly). The escrow scheme avoids it with `receiveWithAuthorization`; a production `exact` variant could do the same with a router as `to`. Demonstrated by e2e `an authorization consumed outside the log leaves no receipt...`.
2. **Wash trading.** Each review is weighted by what its author paid the agent, but an agent owner who pays its own service from an unrelated wallet gets the money back, so it can buy weight at the cost of gas. Receipts raise the cost of spam; they do not prove independent clients. ERC-8004's client filter on `getSummary` is kept mandatory for that reason.
3. **Dust receipts still count.** A receipt of one base unit backs one feedback entry and is included in the `count` returned by `getSummary`; only its weight in `summaryValue` is negligible. Readers should rank on the weighted value, or filter clients. Demonstrated by `test_DustReceiptBuysDustWeight`.
4. **Delivery hashes are commitments, not proofs.** The escrow releases on the payee's word. Mis-delivery is handled by reputation (the release creates a receipt that backs negative feedback) and by the validation registry, not by an on-chain dispute.
5. **Policy changes and the window guarantee.** The rolling-window invariant holds for intervals in which the account does not change its own limits. Lowering the budget takes effect immediately; lengthening the period does not resurrect entries that already expired.
6. **Server replay protection is in memory.** The consumed-receipt set does not survive a restart. A payment served just before a restart can be claimed once more until its claim window (default 600 s after settlement) closes; the on-chain nonce checks still stop it from being settled twice. A persistent store would close this.
7. **Wallet changes within one second.** The wallet history keeps the last change of each second. A receipt is matched against the wallet at the end of its settlement second or of the previous one, which covers changes made in the same block after the payment; a wallet that was set and replaced within a single second, and paid in between, is not matched.
8. **One wallet per agent.** Because a wallet serves one agent at a time, an operator running several agents needs one wallet per agent, and a registrant that already serves an agent registers new ones without a wallet (a deviation from the ERC-8004 draft, which defaults the wallet to the owner).
9. **Validator gas and residual blind SSRF.** Every request that names a validator and is served from the agent's own endpoint costs the validator a response transaction (a hostile requester pays a comparable amount for the request). The agent's endpoint is itself chosen by whoever registers the agent, so the origin restriction of T24 stops a request from pointing anywhere other than its own card, not a hostile registrant from naming any host in that card: such a registrant can still make the validator send a few bounded GETs (any path on that host, only the validator's signature headers, no body, no redirects, timeout, size cap, at most `maxAttempts` per request) to a host of its choosing, and learn only whether a score was posted. A production validator would also refuse private and loopback addresses, which this local stack cannot do (every service runs on 127.0.0.1), and would filter requesters; this one does neither.
10. **ERC-4337 path untested end to end.** `AgentAccount` validates UserOperations signed by the owner (unit-tested), but the local stack has no EntryPoint or bundler; the owner administers the account with direct calls.
11. **Local only.** One settlement asset per deployment, one chain id, no key management beyond in-memory keys generated at start-up.
12. **A lost `202` loses the escrow access token.** The escrow result is served only to the holder of the access token returned with the `202`. If that response is lost, a retry with the same `PAYMENT-SIGNATURE` finds the job already accepted and gets `payment_already_used`, so no new token is issued. The work is still delivered (or refunded after the deadline) and the delivery hash is on-chain, but the payer cannot read the result from this server. Re-issuing a token to whoever presents the same signature would close this at the cost of making the signature a bearer credential for the result.
